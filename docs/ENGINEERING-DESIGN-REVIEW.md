# BraveLife 工程、玩法、UI 与渲染审视

日期：2026-11-03。范围：本地工程静态分析、现有脚本验证、H5 本地构建与桌面实际界面。本文是改造准备与决策建议，不代表已完成新 GDD 或实现改造。

## 决策结论

**需要重新规划核心体验，建议分层改造，暂不整体重写或更换引擎。**

已有资产值得保留：Vue/uni-app 跨端结构、分模块规则、数据化职业与地点、生活数值、剧情条件、等轴房间寻路、账号和云存档。主要短板是产品承诺与可玩内容、时间节奏和界面反馈未形成一致闭环。换成 3D 或全部 Canvas 不会自动解决这些问题。

## 2. 玩法与文档差距

以 docs/STORY.md 为当前已记录方向：温暖、现实挫折、勇气、恋爱、成长和家族传承；保持实时慢节奏，不加入日程快进。以下建议尊重这些约束，改变时需另行决策。

### 2.1 时间尺度必须先明确

默认 1 现实秒 = 1 游戏分钟，纯时钟运行一日约 24 分钟，一年约 146 小时；从 6 岁到 18 岁约 1,752 小时。这是**不计动作推进、睡眠、上学和跳日的时钟基线**，不能当作实际通关时长。即便如此，也说明不能只依赖年龄解锁主线。

建议先测真实玩家完成一日、一周的耗时；让一个年龄阶段内持续有目标与关系变化。若要压缩历法、章节转场或改跳日规则，均属于对现有已定方向的变更，不能悄悄实现。

### 2.2 成年数值目标与人生叙事尺度不一致

balance-sim 在三种背景、每种三次的本次随机运行中：商社最高职位 41–112 天、程序员最高职位 75–89 天、艺人最高职位 35–41 天、当选都知事 29–85 天、声望 100 为 53–68 天、净资产一亿 244–282 天。

这只是自动策略的引擎结果，未计算真人操作与动画时长，也没有固定随机种子，不能外推玩家留存。脚本未传 startAge，走 newGame 默认 22 岁路径，而创角界面提供 6–18 岁，因而主要反映成年经济规则。

应先定义每条路线应承载什么体验，再重定成长节点。优先加入选择后果、关系和叙事里程碑，避免单纯拉长刷数值时间。

### 2.3 阶段和传承尚未闭环

- data/story.js 的 STAGE_GOALS 当前只定义 elem，小学以后的阶段目标没有同等覆盖。
- core.js 的 family 当前只有 gen 与 heirloom；courage.js 已有传家宝相关内容，但未发现完整的生育、接班、遗产税与代际关系迁移链路。不能把初始化字段视为已实现的玩法。
- social.js 有好感、告白等基础，距离文档中的长期同学人生、恋爱名场面和代际人物仍有明显内容工作量。
- 标题页文案强调工作、装修、置业、选举；设计文档强调成长、恋爱、勇气与传承。需要统一“玩家为何回来”的主承诺。

建议下一阶段做“成年独立生活的一周”可玩样段，验证：日常照顾 → 主动做一次有压力的选择 → 获得关系/勇气变化 → 家中留下可见纪念。选择成年样段是范围建议，不意味着删除童年。

## 3. UI 审视

实机桌面截图见 review-assets/desktop.png。水彩纸张与建筑插画具有一致氛围，可以作为主方向保留。

| 观察/证据 | 影响 | 改造建议 |
|---|---|---|
| game.vue 左栏同时常驻 HUD、任务、愿望、技能、快捷键 | 信息竞争、左栏长滚动，场景被遮挡 | 默认仅显示时间、基本需求、当前目标；技能和愿望详情收起 |
| 宽屏 HUD 与底栏都提供速度控制 | 重复入口且数据不一致 | 由唯一 SPEEDS 数据源生成，统一文字与选中状态 |
| city-map 的 pad 全部为零，镜头按整个场景居中 | HUD 覆盖与相机有效视区没有共同边界 | 定义可见安全区域，定位与缩放根据遮挡后的中心计算 |
| 图片建筑作为贴纸，场景装饰道路与实际移动分开 | 玩家难以区分视觉路线与可走路线 | 提供目的地、高亮入口和路线反馈；保持贴纸地图作为旅行导航也可成立 |
| 许多操作使用 view/text 加 click/tap | 键盘、焦点和可访问性语义需补齐 | 对 H5 的主要操作增加按钮语义、焦点状态和完整键盘路径 |

**确定问题：** game.vue 底栏速度数组为 [1,2,3]，themes.js 的 SPEEDS 是 [0,1,2,5]，setSpeed 会拒绝 3，导致底栏“3×”无效。应修复并验证刷新持久化。

建议界面责任：地图负责找目的地；地点面板负责动作与代价预览；家负责照顾和陈列成长；手机负责关系、人生与记录。每个行动在点击前展示时间/金钱/需求，完成后展示结果与下一个可做的事。

移动端已有独立模板，但本次浏览器尺寸模拟未可靠切入移动布局，不能据桌面截图判定移动体验合格；需要真实 390px/小程序设备验证安全区、面板滚动和地图手势。

## 4. 渲染：优先规范与解耦，暂不换引擎

当前不是 WebGL 游戏。城市是背景图 + 绝对定位的 DOM 贴纸，人物以 CSS 元素拼装；房间是 DOM 等轴地板/家具，BFS 寻路，以 CSS transition 和定时器表现移动。

优势：跨 uni-app 端复用、UI 与剧情文本容易维护；当前小场景规模尚无证据说明必须迁移。限制：城市没有沿道路寻路，人物直线移动容易穿越装饰地形；角色与插画的材质需要统一；缺少可测量的资源与帧率预算。

具体工程风险：

1. city-map 在走路动画结束回调中才 travel 结算，组件卸载会清 timer；动画成为规则能否执行的条件。快速切换页面可能取消尚未结算的出行，需要可重复验证，再明确取消或继续的产品规则。
2. iso-room 在 busy 时直接 req.run()，意味着新请求可能在前一动画未完时结算。应统一动作执行中的禁用、排队或取消规则。
3. onGo 用固定 50ms 等待挂载再发请求；应改为组件就绪协议或 nextTick 后的明确确认，避免依赖设备时序。
4. 图片失败标记以地点/家具 ID 缓存，主题切换未见统一重置；建议按资源 URL 记录失败并给出重试机制。

建议逐步建立 ActionController：验证 → 执行/取消策略 → 规则结算 → 存档 → 发送表现事件。动画消费事件，切换场景和跳过动画不得重复扣款或重复完成动作。结算在动画前还是后可选择，但必须有唯一、可恢复的状态归属。

美术先锁一套水彩方向，统一等轴角度、家具脚点、尺寸、阴影、角色比例与色板。三主题可以保留兼容，但新内容先完成主主题，再评估并行制作成本。src/static/h5 约 11MB，images 约 382MB，是不同用途的目录，不能将后者直接视作线上下载体积。

只有在目标设备上证明 DOM 节点、场景动画或镜头效果已达瓶颈，才对“场景层”做 Canvas/WebGL 小样；Vue 继续负责 HUD、面板与剧情。帧率、内存、首屏和触控数据目前未采集，不声称已有性能瓶颈。

## 5. 存档与长期维护

- core.load 按顶层默认值合并，嵌套对象缺字段不会递归补齐；后续新增勇气/家族字段时有风险。
- account.loadFromSlot 与本地 load 采用不同迁移代码，本地针对旧 profile.birth 的兼容没有复用于云端恢复。建议建立唯一 migrateSave(raw) 并做结构校验。
- 页面 onHide/onUnload 仅关闭时钟和键盘；实时进度每 30 游戏分钟落盘，有短时间退出丢进度窗口。建议隐藏时做本地保存并验证生命周期。
- 客户端规则和云端任意存档适合单机体验；若未来引入排行榜或共享经济，必须单独设计可信校验，不能直接复用为公平竞技基础。

## 6. 执行顺序与完成标准

| 阶段 | 工作 | 完成标准 |
|---|---|---|
| P0 基线 | 修速度、统一迁移、明确动作与取消语义、补退出保存 | 无效速度消除；同一存档本地/云恢复一致；途中切页不重复结算 |
| P1 可玩样段 | 成年一周，职业、关系、勇气各一条短链路 | 玩家能解释今日目标、关键选择和结果；不靠指导找到下一步 |
| P2 UI 原型 | 手机优先的地图/地点/家/手机/剧情，桌面同一信息架构 | 逐页覆盖空、加载、失败、不可用状态，真实设备完成闭环 |
| P3 表现统一 | 主主题规范、角色/家具脚点、路线与镜头反馈 | 代表性场景一致；测量目标设备后决定是否迁移场景渲染 |
| P4 内容扩张 | 其他年龄阶段、长线恋爱、代际传承 | 每阶段目标与事件有对应数据、界面和存档迁移，不只列功能名 |

当前不建议直接开启全量美术替换、全面引擎迁移或大规模新系统。先使上述样段可玩、可验证，再按样段反馈扩张。

## 7. 技能研究与安装记录

来源：https://github.com/link1230/game-design-skill ，固定提交 b2b3c8e0bed2720fb1d6a03f1a75334c51bb49a7。

仓库是 Reasonix Skill Pack，包含 game-system-design、game-ui-prototype、game-design-gdd、game-asset-requirements、game-design-to-report，共五个 Markdown 技能。它们用于策划、原型、GDD、资源与汇报，不是游戏运行时或渲染引擎。

原仓库没有 Codex 所需的 <技能名>/SKILL.md，因此无法直接交给标准 GitHub 技能安装脚本。已保留每个 Markdown 的原文与 YAML 元数据，以对应名称的 SKILL.md 安装至 /Users/pro/.codex/skills，并为各目录附带生成脚本及 SOURCE.md 溯源。未安装仓库的 node_modules，未执行其生成脚本。

局限：原文仍使用 Reasonix、ask_choice、write_file 等平台称谓；报告技能引用 ppt-master 等外部工作流，不能据此保证在本环境直接运行。随附 gen_* 是具体示例生成器，使用前需检查内容、输出路径与依赖，不应当作可泛化的生产管线。技能中的审美规则（例如避免三栏）是启发，不应压过本项目已有方向和试玩证据。

本轮完成安装与适用性研究，没有启动要求逐步确认的正式五件套生成流程；后续可先用系统设计形成初稿，再做 UI 原型、对齐 GDD、资源清单与汇报。

优先决策：首个版本主打成年独立生活，还是完整成长？多年历法是否保持原规则？恋爱与传承何者是近期必须交付？这些影响后续 GDD，但不影响先修 P0 与制作可玩样段。没有用户试玩数据前，对“好玩程度”的结论仍是基于机制与内容覆盖的工程判断。
